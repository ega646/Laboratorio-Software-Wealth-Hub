# UC02 + UC05 — Decisiones de implementación

## Contexto

UC05 (actualización de precios) se implementó antes que UC02 (detalle e inversión) porque
UC02 necesita datos reales en `valorhistoricoactivo` para mostrar el gráfico. Con los datos
seed del sprint anterior ya existe historial de 7 días por activo, así que UC02 funciona
desde el primer momento.

---

## UC05 — Actualización de precios

### APIs externas elegidas

- **CoinGecko** para activos de tipo `CRYPTO`. No requiere clave en el tier gratuito
  (hasta 10–30 req/min). Se usa el endpoint `/simple/price` pasando IDs de CoinGecko
  (p. ej. `bitcoin`, `ethereum`) y las divisas de cada activo.
- **Alpha Vantage** para activos de tipo `INVERSION`. Requiere `ALPHAVANTAGE_API_KEY`.
  Se usa el endpoint `GLOBAL_QUOTE` con el ticker estándar de mercado (p. ej. `SPY`).
- Los activos de tipo `PROPIEDAD` no tienen fuente de precio automática: el usuario los
  actualiza manualmente. Se ignoran si tienen `simbolo = NULL`.

### Columna `simbolo` en la tabla `activos`

Se añadió una única columna `simbolo VARCHAR(50)` para almacenar el identificador externo:
- Para `CRYPTO`: símbolo de mercado estándar (`BTC`, `ETH`). El código mapea internamente
  `BTC → bitcoin` para CoinGecko via `COINGECKO_IDS` en `lib/utils/precios.ts`.
- Para `INVERSION`: ticker de Alpha Vantage directamente (`SPY`, `VWRA`).
- `NULL` indica precio manual (PROPIEDAD, EFECTIVO).

Una sola columna evita complejidad. El mapa CoinGecko vive en código porque es estable
(el ID `bitcoin` nunca cambia) y no requiere una tabla extra.

### Arquitectura de la lógica de precios

La lógica de fetch + upsert está en `lib/server/actualizarPrecios.ts` y es importada por
dos rutas distintas:
- `POST /api/precios` — llamado desde el botón "Actualizar precios" del dashboard.
  Requiere que el usuario esté autenticado.
- `GET /api/precios/cron` — llamado por Vercel Cron una vez al día (01:00 UTC).
  Protegido con `CRON_SECRET` en lugar de sesión de usuario.

Ambas rutas usan `createServiceClient()` (service role key) para el upsert en
`valorhistoricoactivo`, que solo tiene política de lectura pública. Así no es necesario
añadir políticas de escritura a esa tabla.

### Cron automático

`vercel.json` define `"schedule": "0 1 * * *"` (diario a las 01:00 UTC). Vercel incluye
el header `Authorization: Bearer <CRON_SECRET>` automáticamente.

## UC02 — Catálogo y detalle de inversión

### Corrección de bugs en `[id]/page.tsx`

La página preexistente usaba `activo.ticker` y `activo.nombre`, campos que no existen
en el tipo real devuelto por la API (`ActivoPoseidoConPrecio`). La reescritura usa:
- `activo.activos?.descripcion` para el nombre.
- `activo.activos?.simbolo` para el ticker/símbolo.
- `activo.historico` (datos reales) en lugar del array mock de ceros.

### Componente `PriceChart`

Extraído a `components/PriceChart.tsx` para ser reutilizable en UC04, UC11, UC12 y UC13.
Maneja internamente la inversión del orden (la API devuelve fecha descendente, el gráfico
necesita ascendente) y el formateo de fechas en español.

El dominio del eje Y se calcula con padding del 10% para que la línea no quede pegada al
borde del gráfico cuando los valores tienen poca variación.

### Catálogo (`/dashboard/catalogo`)

- `GET /api/catalogo` filtra por `tipocodigo` en la BD y por nombre en memoria. El
  filtro de nombre se hace en memoria porque el volumen de activos es pequeño y evita
  añadir búsqueda de texto completo en Supabase.
- La página carga en paralelo el catálogo y los activos del usuario para marcar los que
  ya están en cartera, sin añadir un campo extra a la API del catálogo.
- Los filtros de tipo son botones toggle (no un select) para facilitar el uso en móvil.
